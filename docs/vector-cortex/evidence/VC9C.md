## Evaluation

- The Cortex sub-tab is a pure consumer of VC9A/VC9B: it polls `GET /api/setup-cortex-status`, renders the status payload's aggregates (mode A/B/C, asset digest prefix, qualification verdict + threshold failures, open blockers, encoder health, `VcStatusBadge`), and drives `POST /api/setup-cortex-action` / `GET /api/setup-cortex-action-log`. No server logic touched; no endpoint registry change; never surfaces payload bytes/prompts/ledger (EVAL-REDACT-002).
- Every action button uses the `ActionDef` + `window.confirm` pattern and the POST body always carries `confirm:true` (the server hard-requires it). A 423 `action_blocked_by_open_item` surfaces the gating blocker ids and highlights the matching blocker rows; a 400 `confirmation_required` and a 404 disabled state are rendered honestly (never swallowed).
- The sub-tab is hidden (filtered from `SUB_TABS`) when the VC9A status payload reports the off/disabled shape (`enabled:false` / `status:"off"`), matching the VC0E honest-status gating; `MEGACOMPACT_VC9C=0` is byte-identical to the VC9B-era Setup tab.

## Offline/network/asset/platform evidence

The client api module uses only relative loopback `fetch` paths against the local dashboard server (PREVENT-PI-004); no external network. All action/log responses are aggregates (digest prefixes + codes + user-invoked log tails); the sub-tab never writes or mutates state. Platform-neutral: it renders whatever the status payload reports.
