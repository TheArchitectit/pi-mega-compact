# DASH-MULTI-PI — Multi-pi real-time stacked memory graph

**Status:** planned | **Depends on:** DASH-0d (7-surface consolidation), VC9A-D (setup cortex surfaces) | **Phase:** DASH
**Flag:** `MEGACOMPACT_DASH_MULTI_PI`, defined in `src/config/vector-cortex-dash-multi-pi.ts` (sibling extract), re-exported by `vector-cortex.ts` + root `src/config.ts`, default ON; `MEGACOMPACT_DASH_MULTI_PI=0` disables and must be byte-identical to the DASH-0d predecessor — the 7-surface set renders without the multi-pi overlay, the server omits all new multi-pi endpoints and fields. ## Goal and inputs/outputs

**Deliver a real-time stacked token-context graph across active pi sessions on the Memory Graph surface.** The dashboard already aggregates across repos via `~/.mega-compact-index/index.sqlite` `repo_registry` and renders an `ActiveReposTable` from `/api/servers` — but it is a point-in-time table, not a graph, and seven gaps prevent a real-time multi-pi stacked view:

1. **No heartbeat** — `repo_registry.last_seen` updates only on `bindRepo` (repo-switch), not per-turn. A 30-min-stale `last_seen` does not mean dead. Need a periodic heartbeat per active session.
2. **No per-session token time-series** — `dashboard.json` is a single replaced snapshot; `perf_samples` lacks context-token count; `events.log` has `fromTokens/toTokens` only on compact events (sparse). Need append-only `token_samples(ts, session_id, repo_root, tokens, percent, context_window)`.
3. **No multi-session registry** — `repo_registry` is one row per repo; concurrent pi processes in the same repo collapse to one row. Need a per-PID/per-session registry.
4. **No cross-process live-snapshot store** — each pi writes its own per-repo `dashboard.json`. Need shared index appends, or the server enumerates active state-dirs via a registry and reads each repo's dashboard.json on each poll.
5. **No charting capability in client** — the client has only CSS div-bars (`ContextGauge`, `PerfChart`). Need a lightweight charting approach (hand-rolled SVG stacked area chart — NO new npm dependency, to keep the bundle minimal and avoid supply-chain risk).
6. **No `/api/sessions/timeseries` endpoint** — `/api/servers` returns the latest point only.
7. **`overlayCurrentRepo` overlays only the launcher's own repo** — needs to overlay every active session.

This sprint closes all seven gaps behind `MEGACOMPACT_DASH_MULTI_PI`. The flag-off path is byte-identical to the DASH-0d 7-surface set (no multi-pi overlay, no new endpoints, no new client chart component).

Inputs: the existing `~/.mega-compact-index/index.sqlite` `repo_registry` (WAL, multi-writer safe), the per-repo `dashboard.json` snapshot files, the `events.log` SSE tail, and the `perf_samples` table. Outputs: three new server endpoints (`GET /api/sessions` — live multi-session registry; `GET /api/sessions/timeseries?window=300` — append-only token time-series; `GET /api/sessions/heartbeat` — heartbeat receiver), one new SQLite table (`session_registry` + `token_samples`), one new client chart component (`StackedTokenGraph.tsx` — hand-rolled SVG stacked area chart), and an additive overlay on the Memory Graph surface.

## Failure triad and independence

A **multi-session registry**: when two pi processes run concurrently in different repos, `GET /api/sessions` returns two `SessionEntry` rows with distinct `sessionId` and `pid` values, and each has a fresh `lastHeartbeat` — pinned by **MULTI-PI-001** (multi-session registry) and **MULTI-PI-002** (concurrent same-repo sessions do not collapse — per-PID distinction). B **token time-series**: `GET /api/sessions/timeseries?window=300` returns `TokenSample[]` with monotonically increasing `ts` values per session, and the stacked sum does not exceed the context window — pinned by **MULTI-PI-003** (time-series ordering) and **MULTI-PI-004** (stacked sum within bounds). C **flag-off + heartbeat**: `MEGACOMPACT_DASH_MULTI_PI=0` omits all three endpoints (404), the Memory Graph tab renders the DASH-0d predecessor byte-identically, and the runtime heartbeat hook is never registered (zero overhead) — pinned by **MULTI-PI-005** (flag-off byte-identical) and **MULTI-PI-006** (contract additivity). A is produced by the registry module; B by the time-series query; C by the flag/absence branches. Independence: the registry is isolated from the route layer; the time-series query is a separate endpoint; the flag-off path is verified byte-identical.

## Migration, privacy, dashboard, and rollback

Migration disposition: **additive — two new tables (`session_registry`, `token_samples`) in the existing `~/.mega-compact-index/index.sqlite` via `CREATE TABLE IF NOT EXISTS`.** No existing table is altered; no data is migrated. The tables are created on first access (lazy migration, same pattern as `src/store/sqlite.ts`). A `stateDir` downgrade (flag-off) does NOT drop the tables — they simply stop receiving writes; the data is preserved for re-enablement. Privacy follows [SECURITY_PRIVACY](../SECURITY_PRIVACY.md): `token_samples` carries ONLY aggregate token counts, percentages, and context-window sizes — NEVER message content, NEVER embeddings, NEVER user payload. The `session_registry` carries PID + repo-root (filesystem path, not content) + timestamps. The heartbeat does NOT log to `events.log` (it writes to `token_samples` instead, avoiding log-volume inflation). Dashboard: the Memory Graph surface gains the stacked token chart; `cd extensions/dashboard-client && npm run typecheck && npm run build`. Three new routes registered. Rollback sets `MEGACOMPACT_DASH_MULTI_PI=0`; the three endpoints return 404, the Memory Graph tab renders the DASH-0d predecessor byte-identically, and the runtime heartbeat hook is never registered (zero overhead). The `session_registry` and `token_samples` tables are NOT dropped (data preservation). No operator migration.
